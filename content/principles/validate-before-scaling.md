# Validate Before Scaling

It is tempting to believe that if you build a robust, highly scalable system, users will naturally come. As engineers, we love designing architectures that can handle millions of requests. We want to automate everything from day one.

But scaling an unvalidated idea is one of the most expensive mistakes a founder can make.

## The Principle

**Do not build infrastructure for a problem that you haven't proven people are willing to pay to solve.**

## The Illusion of Scale

When you focus on scaling early, you focus on the wrong metrics. You optimize databases instead of optimizing the value proposition. You build automated onboarding flows for users who haven't even signed up yet. 

You build a machine before you know if anyone wants the product the machine produces.

## Validate First

Validation means finding the truth as cheaply as possible.
- If you have an idea for a coordination tool, don't build the app. Try to coordinate a single event using a simple spreadsheet you designed, and see if the organizer finds it valuable.
- If you think trust is a problem, don't build a verification platform. Try to manually verify vendors for one planner and see if they actually care.

If the manual, unscalable version of your idea doesn't create value, the automated, highly scalable version won't either.

## Do Things That Don't Scale

In the early days, you *should* do things that don't scale. You should manually onboard your first users. You should handle edge cases yourself instead of writing code for them. 

Once the manual process becomes too painful because there is so much demand, *then* you write the code to scale it. Code is the reward for finding a real problem.
